Internal Spec — v1

Topic-to-Video Pipeline

An automated pipeline that takes a topic as input and produces a finished, voiced, vertical video — the same process used by hand for the Mayweather, JPMorgan, DSCR, and construction-loan videos, now specified as a repeatable system. Orchestrated with the Workflow tool: judgment-heavy steps run as agent calls, deterministic steps (rendering, muxing, file checks) run as plain code between them.

00Input

topic (required) — a working title or short description, or a source URL/article when the topic is tied to a specific piece (like the Trilith blog post). Optional: brandFlag (whether to include client branding in the closer), target duration range.

01Research & Facts

agent · web search/fetch

Web-searches the topic, cross-checks 2–3 sources, extracts dated facts with citations. Flags when hard numbers are missing (as the construction-loan article did) rather than inventing them. Output shape matches the existing data/topics_*.json format.

02Hook + Script

agent reads hook_templates_1000.json

Selects a category and a specific template from the 980-template hook library (hook_templates_1000.json — Educational, Storytelling, Authority, Myth Busting, Comparison, Day in the Life, Random), then fills its (insert X) placeholders with real facts from Stage 01. Example: "This represents your X before, during, and after X" → "This represents your credit score before, during, and after a DSCR loan."

Writes the full 10–12 beat script (line + estSeconds per beat), same shape as data/script_*.json.

03Visual Plan

agent + JS validation

Maps each beat to a component from the existing Remotion library (Card, GiantStat, BuildList, DocumentCard, a bold-statement full-bleed, a twin-split, a step-process visual, the signal-pulse closer, an opening full-bleed). Hard rule enforced in code, not just prompted: no two consecutive beats use the same component. Beats needing a real photo/video are flagged for Stage 04.

Large, varying text — enforced, not suggested Every beat also gets a text-size tier for its dominant text element — giant (140px+), large (95–140px), or medium (60–95px) — and the same no-repeat rule applies to this tier as to component choice: no two consecutive beats share a size tier. This came out of repeated feedback across all four hand-built videos ("make it a lot bigger") — baking it into the plan means every future video starts oversized instead of needing a second pass to fix it.

04Asset Search

agent, per flagged beat

Searches Pexels' video endpoint only — this is a hard rule, not a preference: the search call itself is never allowed to hit the photo or GIF endpoints, so a static image can't enter the candidate pool in the first place. Uses 2–3 keyword variations derived from that beat's actual line (not one generic topic keyword). Returns 3–5 candidate clips per beat, ranked by relevance guess, for Stage 05 to work through in order.

05Asset QA

Two tiers, cheapest check first, so a bad candidate never reaches a model call it doesn't need.

Tier 1 — Format & motion deterministic, no model call
  • Must be a video file. Any non-video candidate is rejected before this tier even runs (Stage 04 only queries video search).
  • Extract 3 frames via ffmpeg (start / mid / end). Compute a perceptual difference between them.
  • Near-identical frames → static/boring clip → auto-reject, no vision call spent.
Tier 2 — Vision judgment agent call on the 3 sampled frames

The agent receives the 3 frames, the beat's specific line (not the general topic), and the on-screen caption. Structured output:

FieldChecks
relevantWould a viewer immediately connect this footage to this exact line? Generic topic-adjacent stock (e.g. handshake footage for any finance beat) fails even if thematically nearby.
visuallyInterestingReal composition and lighting, not the generic locked-off corporate-stock look; no dead space; no burned-in watermark or logo.
verticalCropOKWould a 9:16 cover crop cut off or squeeze out the interesting content?

relevant and visuallyInteresting are the real pass/fail gate. verticalCropOK is not — it routes the asset to a rendering mode instead of rejecting it (see below).

Crop failure ≠ rejection A clip that's relevant and interesting but doesn't survive a 9:16 cover crop isn't thrown away — Assembly renders it contained on a white frame instead (the clip shown in full at its native aspect ratio, letterboxed on the app's white background token, same as a photo inset in a Card) rather than force-cropping it and losing the subject, or discarding a genuinely good asset over an aspect-ratio mismatch.
Retry & fallback On a relevant or visuallyInteresting reject, try the next candidate — up to 4 attempts per beat. If nothing passes, that beat falls back to a graphic-only scene (no photo/video). No silent settling for a clip that merely "sort of" fits — this was the exact failure mode that produced the disliked brick-wall photo before a human had to catch it by eye.

06Assembly

agent, writes the .tsx

Generates the actual Remotion composition file from the visual plan + script + approved asset paths, importing the shared component library rather than regenerating component code from scratch each run. New composition registered in Root.tsx with a placeholder duration (corrected in Stage 07).

07Voiceover

agent, runs the ElevenLabs step

The timestamp-driven approach proven across the last three videos: one continuous ElevenLabs take with word-level alignment, real per-scene durations computed from the actual audio, then written back into the .tsx scene durations and Root.tsx's total duration — the video is timed to the voice, never the other way around.

08Render, Mux, Approval

agent, Remotion + ffmpeg

Final remotion render, ffmpeg mux of video + narration, then the finished file is returned for human approval — the pipeline does not auto-publish or auto-deliver anything. Same review gate used for every video so far.
